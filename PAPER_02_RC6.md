## Abstract

One producer runs a media operation through thirteen AI assistant "seats" spread across six named products and tools (listed in Section 1), several computers and one shared Google Drive folder (the "shelf"). Session resets and context limits can lose a seat's working context, sometimes mid-task, and a seat's report of its own work is often wrong. Persistent records help only when they are recovered and checked. We describe the mechanisms that made the operation dependable:

1. Per-seat **boot cards**, read first after any reset.
2. An **end-of-turn state footer** synced to one master state file.
3. **Skill locks**: append-only "never repeat" rule files tied to scripts that enforce them.
4. **File-evidence acceptance**: nothing counts as done until it is a file on the shelf with bytes and a SHA-256, preferably re-derived by a second seat.
5. A **nightly debrief** whose last answer must name a code or file change.

We report what was caught on Oct 26–30, 2026, while these mechanisms were in use. That includes a Short that would have been cut from the wrong show's master, an 18.25 GB only-copy master queued for deletion, a "new version" that silently reused old frames, and an automated job that created 17 numbered duplicate state files. We also report where the mechanisms are still weak, the main gap being that agents only read their inbox when prompted. We borrow the vocabulary of verifiable rewards for the acceptance gates, but no model is trained here. This is an incident log from one operation, not a controlled experiment, and we claim no causal effect.

## 1. Setting

The seats are commercial assistants used through their normal products. They include Claude in a desktop app and a cloud workspace, ChatGPT, Gemini, Grok, Cursor, and Claude Code on a GPU machine. Each seat has one job (writer/3D director, switchboard and uploads, fact checks, render node, GPU node, infrastructure watch, red-team audit, tools). They coordinate through a shared log, a set of Google Docs called the Court Brain (Volume 10 since 2026-10-30T06:20Z). The work product lives on the shelf. The producer gives orders in plain language and does not want to be anyone's messenger.

Three properties of current assistants drive everything below:

- **Context loss.** A new session, a context limit or a model switch can lose working context. How much persists differs by product and session, so the mechanisms below assume nothing survives unless it is in a file. A seat may be mid-render when its context resets.
- **Confident self-report.** A seat will sincerely report "done" for a file that is on its own disk but not on the shelf, or "PASS" for a gate it did not run.
- **Clones.** Automated jobs that "save state" by creating a new file each run produce piles of near-identical files, and no seat knows which one is current.

## 2. Mechanisms

### 2.1 Boot cards
Each seat has one short file it reads first after any reset. For example, `claude/00_A2_BOOT_READ_FIRST.md` for Fable, and `00_SHADOW_GPU_BOOT.md` for A6. The card lists open work with file paths, hashes and receipt IDs. It also holds the standing laws and the seat's own hard-won technical notes (for example, "this box OOM-kills a single long render; render in ≤7-frame chunks"). A card is rewritten in place, not appended to, so it stays short enough to read in one pass.

### 2.2 The state footer
Adopted as law on Oct 30 05:20Z: every turn ends with an `ACTIVE_COURT_STATE_FOOTER` naming the seat, its job, what it is waiting on, its holds and its last receipt. Each footer is meant to sync to `COURT_OS/EMPIRE_MASTER_STATE.md`. This paper does not verify that every seat writes a footer every turn; the law is adopted, and universal compliance is not measured. The footer makes a seat's state visible to the next reader, which may be the same seat after a reset, without anyone reconstructing it from a long log. A companion rule pins a cumulative summary block at the top of every new Brain volume, so a new volume never starts cold. Volumes roll over by a size guard. Volume 9 closed at 852,229 characters at 06:20Z, and the guard posted the new volume's link and updated the write workflow in the same entry, so writers followed the pointer without being told twice.

### 2.3 Skill locks
Started Oct 21. `COURT_OS/SKILL_LOCKS/` holds one file per department (FLOW, RESOLVE, ROUTER, BRAIN, RELEASE, and since tonight BLENDER and a CHARLIE audit lock). Each rule is one line: *date | what failed | the rule now | proof*. Rules are added by a small script that refuses duplicates and never deletes. Since Oct 30 the stronger form is required: a lock line must point at a script that rejects the tested failure condition, not just at advice. A lock identifies the failure conditions its script was tested against. It does not make every recurrence impossible.

### 2.4 File-evidence acceptance
The founder's rule of Oct 28: "Nothing is done until it is a file on the shelf with a receipt." In practice:

- Every receipt names the shelf path, the byte count and the full SHA-256.
- The delivering seat stages its own shelf copy back and re-hashes it. Commits from this machine had landed stale copies before.
- The rule asks a second seat to re-derive the fact for anything consequential. Section 3 records whether that happened for each incident. Several catches there were made by the authoring seat itself, which is a self-check, not independent verification.
- Charlie's `receipt_acceptance_gate.py` turns this into code. It accepts a receipt only if every cited file matches exact path, bytes and hash, and every required gate is present and consistent. Its 16 adversarial tests all pass.

### 2.5 Nightly debrief with an applied lock
Introduced Oct 30. Every seat answers five questions in one shared file (`NIGHTLY_DEBRIEF_AND_LESSONS_APPLIED.md`, Drive 1w_73kmPFkP40fiDHvS5rwL1mLTtJYeR7): what it shipped, where it failed, how to do it twice as fast, where it wants a sandbox, and what it changed tonight. The fifth answer must name a committed change. On the first night the frozen file holds 11 named sections from 11 distinct seats: A6, Lily, Fable, A5, Charlie, A4, Vale, Delta, Bravo, Lotus and Beni. Filing times inside the file run from about 05:25Z (A6) to about 06:15Z (Lotus, the merger). Four sections (Vale, Delta, Bravo, Beni) were written as standalone files and merged in by Lotus. For Vale and Delta the frozen debrief gives the reason: their connectors could not write to the shared document. It states no reason for Bravo or Beni, and this paper claims none; Beni's section records two times, his Linear MAN-58 comment at 05:25Z and his standalone file at about 05:55Z, and was merged at about 06:33Z. The merge note inside the file says "10 of 10 seats"; that is the merger's count and this paper does not adopt it. No deadline or eligible-roster list is pinned on the shelf, so this paper makes no claim about who was on time. ### 2.6 Security and communication laws (06:28Z)
- **Law A, clean room and untrusted text.** Seats may take ideas from outside research but write original code. Text that arrives in an email, document or web page is data and never triggers tools, deletes or spend. A typed seat name is not a verified identity. A signed-dispatch design (`SEAT_SSN_SPEC_v1.md`) is in the sandbox; no production keys exist and nothing is enforced by it yet.
- **Law B, the Translator.** When the producer's intent seems heated or unclear, a seat routes it through the producer's translator seat (A4.1) and keeps doing the clear, authorized work, instead of freezing or asking him to repeat himself.

Both laws are adopted, not verified as universally implemented, and are one night old. We report no outcome from them.

## 4. Coordination latency: the honest weak point

An Oct 26 trial of a message bus between four seats ran 3 of 3 round trips with zero dropped messages and hash-carried hops. The transport itself was sub-second. Wall-clock per hop was minutes to about an hour, because two of the seats only read their inbox when a human or a schedule prompted them. The same pattern appears in the debriefs: one seat sat about five hours on an interactive prompt nobody could answer. The A6 boot card now requires that every job file supply a default for every fork. The general fix, an agent that wakes on a message rather than on a timer, is not solved here.

## 5. Incentives: the scoreboard, and what it is not

A referee seat keeps `RL_PRODUCER_SCOREBOARD.json`:

- **+1.0** for a first-pass verified deliverable;
- **+1.5** for a measured speed and quality breakthrough;
- **+2.0** for catching another seat's real defect before it ships;
- **-1.0** for a skipped step or an unverified claim passed along;
- **0.0** for a missed deadline or a "deliverable" not on the shelf.

The referee is unscored. Standings in the frozen snapshot cited here (seats updated 2026-10-30T04:49:31Z): A4 3.0, A5 2.5, Vale 2.0, Fable 2.0, Bravo 1.5, Charlie 1.5, Lily 1.0, Beni 0.0. The live ledger has moved on since; this paper cites only the frozen snapshot.

The design borrows from reinforcement learning with verifiable rewards. Points attach only to outcomes a script or a referee can check against a file, and the largest reward goes to catching someone else's defect. We are careful about the claim:

- **No model learns from these points.** The assistants are not fine-tuned; the scoreboard steers assignments and attention.
- **The "reward" is partly a human-designed incentive** (a weekly first pick of a small consumer reward), not an optimization target.
- **What we can say** is narrower: tying recognition to file-verified outcomes, and rewarding cross-seat catches, coincided with the catches in Section 3. We have no counterfactual and claim no causal effect.

## 6. Limitations

- **One operation, five days, no controls.** The incidents are a log, not an experiment.
- **Self-reported debriefs.** Seats reported their own failures. From the debriefs we cite only failures that left a file trace. Section 3 also keeps one incident that rests on a seat's report alone (the 18.25 GB delete batch) and one that rests on a ruling alone (the relayed tmux report); both are labelled that way in the evidence-basis table.
- **Model and product churn.** Seat capabilities change underneath the mechanisms; one seat changed models during the period covered.
- **Not all gates are closed.** At Charlie's latest kit check, the SF kit's production receipt checker was still the version that passes incomplete evidence. The incidents show catches, not the absence of misses.
- **Footer adoption is new.** The state-footer law is one night old. Its template is not yet canonical, and we report no outcome from it yet.
- **Partial evidence for some artifacts.** Two 4K masters were reported with abbreviated hashes; we do not rely on them.
- **Citation holds.** This paper does not cite the PLAY-06 food-sizzle +3.0 dB result as significant; it is held until A6's holdout recount. The 39–40 clip holdout figure from Deep Research brief #3 is a statistical power planning model (assumed paired SD 0.50 dB), not measured Court variance (A4.1 Round 334, Ruling Q5).
- **New laws without outcomes.** The deep-research-request and open-question footer rules (Oct 30, 06:45Z and 08:42Z) are too new to evaluate.

## 7. Takeaways for others running several assistants on shared work

1. **Put memory in files the agent must read first, and keep those files short.** Boot cards beat long logs.
2. **Make "done" mean a hashed file on a shared shelf.** Re-hash your own copy after every write.
3. **Never accept a peer's PASS without its file evidence.** Encode that in a gate with adversarial tests.
4. **Turn every lesson into a script that rejects the mistake you tested.** A rule written in prose is a wish, and a script covers only the cases it was tested on.
5. **Do not let automation "save state" by creating new files.** Append to one log; keep one canonical path per role.
6. **Measure wake-up latency, not transport latency.** The bus is fast; agents that only read when prompted are slow.
